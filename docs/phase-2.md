# مرحلهٔ دوم — تحویل ویندوز و شواهد واقعی

محصول: Bridge Coding Harness، نسخهٔ 0.2.0. این گزارش مربوط به اپ مستقل است.

## وضعیت پذیرش

ساخت و نصب دسکتاپ و آزمون مدل واقعی دو شاهد جدا هستند. پاس‌شدن demo، وجود API key
یا سبزبودن build به‌تنهایی اثبات اجرای مدل واقعی نیست. وضعیت دقیق هر کدام در گزارش‌های
checks/phase-2 ثبت می‌شود. تا پاس‌شدن real-provider.json، پذیرش سرتاسری provider باز است.

## اصلاح مرحلهٔ دوم

محیط اولیه فقط Python داشت؛ این برای presetهای JS/TS کافی نبود. تصویر مستقل
`bridge-coding-sandbox:0.2` ساخته شد؛ تصویر برنامهٔ مبدأ تغییر نکرد.
Node 24 و npm از تصویر رسمی با digest ثبت‌شده در Dockerfile وارد محیط شدند.
Python، git و ripgrep حفظ شدند. cache موقت npm در /tmp است؛ root filesystem
همچنان فقط‌خواندنی، کاربر غیر root، بدون capability و شبکه به‌طور پیش‌فرض قطع است.

تست‌های واقعی اضافه‌شده:

- نصب یک پکیج محلی با npm و اجرای npm test در container؛ بدون شبکه.
- کامپایل TypeScript با compiler واقعی dependency پروژه و اجرای JavaScript خروجی.
- نصب wheel محلی با pip و import آن در Python؛ بدون شبکه یا دستکاری Python میزبان.

مجموع تست‌های مرتبط runtime، confinement، toolchain، اصلاح، readiness و settings:
**۶۲ passed**، بدون skip. این‌ها در کنار ۴۰۵ passed و ۳ skipped مرحلهٔ اول هستند؛
تعدادها با هم جمع نمی‌شوند چون تست‌های مشترک دارند.

## بسته و نصب

نصب‌کننده با نام Bridge-Coding-Harness-Setup-0.2.0.exe و ZIP ویندوز x64 ساخته می‌شود.
backend همراه برنامه frozen است؛ کاربر نهایی به Node/Python میزبان نیاز ندارد.
Docker Desktop و API مدل وابستگی‌های اجرای واقعی‌اند و مخفیانه نصب یا فعال نمی‌شوند.
هویت Windows، shortcut، uninstall و محل دادهٔ Bridge مستقل از Onboard است.
فایل‌ها مطابق تنظیم پروژه بدون امضای ناشر ساخته می‌شوند.

نصب واقعی با NSIS در پوشهٔ اختصاصی آزمایشی انجام می‌شود. پس از هر بازسازی نهایی،
همان artifact نهایی دوباره نصب و آزمایش می‌شود. نسخهٔ قبل از اصلاح toolchain معیار
تحویل نهایی نیست. install.json نتیجهٔ نصب و پوشهٔ installed نتیجهٔ smoke نهایی را دارد.

آزمون packaged/installed از پروفایل و HARNESS_HOME آزمایشی استفاده می‌کند و پنجره،
کلید یا تنظیمات کاربر را جابه‌جا نمی‌کند. برنامه‌ریزی داخل backend frozen نیز تست می‌شود.

## مدل واقعی

real_provider_acceptance.py مدل پیش‌فرض Bridge را از تنظیمات و Credential Manager
می‌خواند؛ کلید را چاپ یا در گزارش کپی نمی‌کند. پروژهٔ Python جدا و بودجهٔ محدود می‌سازد.
برنامه را خود مدل تولید می‌کند؛ reviewer فقط main.py و python check.py را مجاز می‌کند.
اجرای baseline شکست‌خورده و check موفق پس از اصلاح از receipt واقعی Docker خوانده می‌شود.
فایل تست دست‌نخورده و پروژهٔ اصلی تا apply بدون تغییر می‌مانند. demo پذیرفته نمی‌شود.

هیچ دستور شبکه، نصب یا فرمان ناشناخته‌ای توسط این سناریو خودکار تأیید نمی‌شود.
آزمون واقعی فقط پس از ثبت مدل و کلید توسط کاربر در همین اپ اجرا خواهد شد.
